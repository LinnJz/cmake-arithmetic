# 代码评审（Code Review）

代码评审是"发起评审"与"接收反馈"的完整闭环，两个阶段遵循同一核心原则：**先验证后实现，技术正确性优先于社交舒适。**

## 按需加载

按场景加载对应内容，避免一次塞满上下文：

| 场景 | 加载内容 |

## 核心原则

- **先验证后实现**：收到任何评审意见，先对照代码库核实，再决定实施还是反驳。
- **技术正确性优先于社交舒适**：不做表演式附和，不回避技术性反驳。
- **聚焦工作产物，而非思考过程**：评审子代理获得精心构造的评审上下文，而非你的完整会话历史。

## 阶段一：发起评审（Requesting）

派发评审子代理，**早评审、常评审**。

**必须评审：** 每个任务或批次完成后、完成主要功能后、合并到主分支之前。
**可选但有益：** 卡住时（换新鲜视角）、重构前（基线检查）、修复复杂 Bug 后。

**基本步骤：**

1. 计算评审范围：
   ```bash
   # 功能分支：取与主分支的公共祖先，避免把主线其他改动卷入 diff
   BASE_SHA=$(git merge-base origin/main HEAD)
   HEAD_SHA=$(git rev-parse HEAD)
   # 改动尚未提交时：git diff --stat HEAD（工作区+暂存区），并省略 BASE_SHA/HEAD_SHA
   ```
   或用 `scripts/review-scope.ps1` 一键计算。

2. 用 Task 工具派发评审子代理，按 `references/reviewer-prompt.md` 模板填充 prompt。占位符：`{WHAT_WAS_IMPLEMENTED}`、`{PLAN_OR_REQUIREMENTS}`、`{BASE_SHA}`、`{HEAD_SHA}`、`{DESCRIPTION}`。

3. 上下文构造与派发数量的细节见 `references/requesting.md`。要点：**必塞**变更意图、评审标尺、已知约束与风险区；**不要塞**会话历史、你的结论倾向或辩护（会锚定评审者，使其失去独立判断）。diff < ~200 行用 1 个评审者，大变更拆"质量/规格"双轴并行 2 个，安全敏感加 1 个专职审查。

4. 评审子代理**有权运行构建/lint/测试来验证**，而非仅读代码；跑不了须明说"未运行测试"。

收到反馈后进入阶段二。

## 阶段二：接收反馈（Receiving）

评审反馈需要技术评估，而非情感表演。

收到反馈时按序执行：

```
1. READ        完整读完，不急于反应
2. UNDERSTAND  用自己的话复述要求（或提问）
3. VERIFY      对照代码库现状核实
4. EVALUATE    对当前代码库技术上是否成立？
5. RESPOND     技术性确认，或有理有据地反驳
6. IMPLEMENT   一次一条，逐条测试
```

**绝不要：** "你说得完全对！" / "好点子！" / "我现在就实现"（未经验证）。
**而是：** 复述技术要求、提澄清问题、用技术理由反驳、直接开始干活。

**任何一条不明确就 STOP + ASK**——条目可能相互关联，一知半解 = 错误实现。先澄清全部不明确的，再按 阻塞问题 → 简单修复 → 复杂修复 的顺序逐条实施、逐条测试。

详细的按来源处理、YAGNI 检查、反驳时机、常见错误见 `references/receiving.md`。

## AI Slop 专项检查

当被审代码疑为 AI 生成，或用户明确要求检查 AI slop 时，按 `references/ai-slop-checklist.md` 补充检查 27 种模式（防御式编程、过度工程、不必要基础设施、代码膨胀、测试 slop 等）。

**严重度指南：** slop 发现项大多归"轻微/重要"，**不默认致命**——除非其防御式写法实际掩盖了错误（如吞异常导致数据损坏）。

## 工作流集成

**执行计划：** 每个批次后评审 → 拿到反馈、应用、继续；评审若揭示持久的可复用规则/契约变更，沉淀为仓库记忆而非只留在评审评论里。
**临时开发：** 合并前评审、卡住时评审。

## 红旗

**绝不要：**
- 因为"很简单"而跳过评审
- 忽略 Critical 问题
- 带着未修复的 Important 问题继续
- 与合理的技术反馈争论

**若评审者错了：** 用技术理由反驳、用代码/测试证明可行、请求澄清。

## 底线

**外部反馈 = 待评估的建议，不是必须服从的命令。**
验证。质疑。然后实施。不做表演式附和。始终技术严谨。
