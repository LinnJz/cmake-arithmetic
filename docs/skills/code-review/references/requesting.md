# 发起评审（Requesting）

派发评审子代理，尽早且经常评审。核心原则：**早评审、常评审**。评审子代理获得精心构造的评审上下文，而非你的完整会话历史——聚焦工作产物而非你的思考过程，同时保留你自己的上下文用于继续工作。

## 何时发起

**必须：**

- 每个任务或批次完成后
- 完成主要功能后
- 合并到主分支之前

**可选但有益：**

- 遇到困难卡住时（换新鲜视角）
- 重构前（基线检查）
- 修复复杂 Bug 后

## 如何发起

1. 获取 Git SHA：
   ```bash
   # 功能分支：取与主分支的公共祖先，避免把主线其他改动卷入 diff
   BASE_SHA=$(git merge-base origin/main HEAD)
   HEAD_SHA=$(git rev-parse HEAD)
   # 改动尚未提交时：git diff --stat HEAD（工作区+暂存区），并省略 BASE_SHA/HEAD_SHA
   ```
   或运行 `../scripts/review-scope.ps1 [-Target origin/main | -Uncommitted]`（Windows/pwsh）。

2. 用 Task 工具派发评审子代理，按 `reviewer-prompt.md` 模板填充 prompt。

   占位符：
   - `{WHAT_WAS_IMPLEMENTED}` — 你刚完成的内容
   - `{PLAN_OR_REQUIREMENTS}` — 应达到的目标
   - `{BASE_SHA}` — 起始提交
   - `{HEAD_SHA}` — 结束提交
   - `{DESCRIPTION}` — 简要描述

3. 收到反馈后进入 `receiving.md` 的接收协议处理。

## 评审上下文构造

填充模板前，为子代理挑选上下文：

**必塞：**
- `{WHAT_WAS_IMPLEMENTED}`：一句变更意图，不含实现细节辩解
- `{PLAN_OR_REQUIREMENTS}`：评审标尺；无书面需求时让子代理写明"无需求，按代码自洽性评审"
- 已知约束与关键决策：为何如此设计，避免评审者反复猜测
- 风险区：你自己不确定、想重点审查的部分

**不要塞：**
- 完整会话历史、试错过程、思考链——聚焦工作产物而非思考过程
- 你的结论倾向或对改动的辩护——会锚定评审者，使其失去独立判断
- 与本次变更无关的旧代码上下文

## 派发数量

- diff < ~200 行且单模块：1 个评审者
- 大变更或跨多模块：2 个并行——一个按"代码质量/标准"轴，一个按"需求/规格"轴（把 `reviewer-prompt.md` 清单拆两半）
- 安全敏感或关键路径：加 1 个专职安全/回归审查
- 多份产出由主代理汇总去重后再进接收协议

## 运行测试

- 评审子代理有权运行构建/lint/测试来验证，而非仅读代码
- `reviewer-prompt.md` 模板会指示其检测项目测试命令并报告实际结果；环境限制跑不了时须明说"未运行测试"
