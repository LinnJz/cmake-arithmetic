## 验证方式

- 检测项目的测试命令（如 package.json scripts、CMake CTest、pytest、cargo test 等），运行与本次变更相关的测试，报告实际通过/失败

- 环境限制无法运行时，明确标注"未运行测试"，不得假设通过

## 评审清单

**代码质量：**
- 关注点分离是否清晰？
- 错误处理是否恰当？
- 类型安全（如适用）？
- 遵循 DRY 原则？
- 边界情况是否处理？

**架构：**
- 设计决策是否合理？
- 可扩展性考虑？
- 性能影响？
- 安全隐患？

**测试：**
- 测试真正在测逻辑（而非 mock）？
- 边界情况覆盖？
- 需要的地方有集成测试？
- 运行了项目测试套件？实际通过/失败如何？（无法运行时明确标注）

**需求：**
- 满足所有计划需求？
- 实现符合规格？
- 无范围蔓延？
- 破坏性变更已文档化？

**生产就绪：**
- 迁移策略（如有 schema 变更）？
- 考虑了向后兼容？
- 文档完整？
- 无明显 bug？

## 输出格式

### 优点
[哪里做得好？要具体。]

### 问题

#### 致命（必须修复）
[Bug、安全问题、数据丢失风险、功能损坏]

#### 重要（应该修复）
[架构问题、缺失功能、错误处理差、测试缺口]

#### 轻微（锦上添花）
[代码风格、优化机会、文档改进]

**对每个问题：**
- 文件:行号 引用
- 哪里不对
- 为什么重要
- 如何修复（若不明显）

### 建议
[对代码质量、架构或流程的改进]

### 评估

**可以合并？** [是/否/带修复后]

**理由：** [1-2 句技术评估]

## 关键规则

**应该：**
- 按实际严重程度分类（不是所有问题都致命）
- 具体（文件:行号，不要含糊）
- 解释问题为何重要
- 认可优点
- 给出明确结论
- 能运行测试/构建就运行，用实际结果下结论，而非目测代码

**不应该：**
- 不检查就说"看起来不错"
- 把吹毛求疵标成致命
- 对没评审过的代码给反馈
- 含糊其辞（"改进错误处理"）
- 回避给出明确结论
