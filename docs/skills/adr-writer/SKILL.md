# 架构决策记录（ADR）

ADR（Architecture Decision Record）解决"知识生命周期 < 技术生命周期"的问题：记录**为什么做这个选择、考虑了什么替代方案、什么条件下会重新考虑**，而不是只记录"用了什么技术"。让知识生命周期追上甚至超越技术生命周期。

## 核心原则

- 记录的是"**为什么**"，不是"选了什么"。
- **五要素是唯一不可省略的核心**：背景、决策、后果、替代方案、撤销条件。
- **撤销条件最重要**——它让 ADR 成为"可以过期的、基于信息的合理选择"，而不是刻在石头上的决定。条件变了，就重新考虑。
- **不可变原则**：ADR 一旦 Accepted 并合入仓库就不再修改（拼写错误除外）。架构变了，创建**新 ADR** 取代旧的；旧 ADR 保留为历史快照。

## 何时创建（三条件门）

借鉴 grill-with-docs 的克制原则——**有选择地创建，防止 ADR 泛滥**。以下三个条件**同时满足**才值得写：

1. **难逆转**：事后改主意的成本很高
2. **脱离上下文会令人困惑**：未来读者会问"为什么这么做？"
3. **存在真实权衡**：有真正的备选方案，且你因具体理由选了其中一个

任一不满足就跳过：易逆转的决策你会再翻转它；不令人困惑的没人会问；没有备选的就是"做了显而易见的事"，无可记录。

**什么够格（典型四类）：**
- **架构形态与边界**：monorepo、事件溯源写模型、领域边界的所有权（"Customer 数据归 Customer context，其他 context 只按 ID 引用"）。明确的"不做什么"与"做什么"同等重要。
- **带锁定的技术选型**：数据库、消息中间件、认证供应商、部署目标——不是每个库，而是换掉要花一个季度的那些。
- **刻意偏离明显路径**：手动 SQL 而非 ORM、有特定理由的反直觉做法——防止下一个人"修好"它。
- **代码里看不见的约束**：合规限制、外部契约的延迟要求、不明显的备选否决（选 REST 弃 GraphQL 的微妙理由——否则半年后又有人建议 GraphQL）。

## 撰写工作流：记录 → 生成 → 修正

AI 不能凭空推断历史上下文，但能基于口述生成结构化初稿。流程：

1. **当场记录**：决策结晶时立即写，不事后补——记忆会随语境变化而变色。
2. **收集五要素输入**：背景约束（团队规模、技术栈版本、时间压力）、候选方案清单、最终决策与理由。若仓库已有领域词汇表或 CONTEXT.md，复用其术语。
3. **生成初稿**：按 `references/adr-template.md` 生成结构化 ADR；也可套用 `references/best-practices.md` 中的 AI Prompt 模板。轻量决策用"单段式"（一段话覆盖五要素实质），重大决策用完整模板。
4. **修正定稿**：与团队讨论完善初稿，确认状态、后果（≥2 正面 + ≥2 负面）、撤销条件。

**脚手架**：用 `scripts/new-adr.ps1` 自动编号并创建 `docs/adr/NNNN-{slug}.md`。`docs/adr/` 目录**懒创建**——第一次真正需要时才建立。

## 生命周期与状态

```
Proposed（提议中） → Accepted（已接受） → Deprecated（已弃用）
                          ↓
                        Superseded（被取代）
```

- **Proposed**：初稿，团队仍在讨论
- **Accepted**：团队达成共识，开始实施
- **Deprecated**：不再适用，但未被特定新决策替代
- **Superseded**：被新 ADR 明确取代——**新旧 ADR 必须双向引用**（旧 ADR 记"被 ADR-XXX 取代"，新 ADR 记"取代 ADR-XXX"）

**定期审查**：每 6-12 个月审查一轮，关注：撤销条件是否触发、业务规模是否超出 ADR 假设、技术栈是否有重大更新、团队规模/组织是否变化。审查结果三选一：保持有效 / 标记 Deprecated / 创建新 ADR 来 Supersede。

## 状态索引与决策链

ADR 积累到 10 份以上时，在 `docs/adr/README.md` 维护**状态矩阵**——30 秒看懂整个系统的架构决策全景，新成员优先读 Accepted 的。模板见 `references/index-template.md`。超过 20 份时用 Mermaid/Graphviz 绘制决策关系图。

**ADR 间四种关系**（在新 ADR 的「关联ADR」小节标注）：
- **Supersedes**（取代）：替换旧决策 → 需双向引用
- **Depends on**（依赖）：本决策成立依赖另一决策；被依赖者变 Deprecated/Superseded 时，触发本决策重新评估
- **Refines**（细化）：对高层决策的实现层细化
- **Related to**（关联）：同领域但无直接依赖

## 维护与审计

- 状态变更写入 ADR 内置的「变更历史」表（日期/变更类型/原因/操作人）——支撑审计追溯（"这个决策何时失效、为什么、谁决定的"）与失效模式分析（多个 ADR 同因失效 = 系统性信号）。
- 每季度可用 AI 做一次状态审计：找出已过时未标记的 ADR、未记录的冲突/重叠、已触发的撤销条件，生成"状态异常 ADR 清单"。触发时机：新 ADR 创建时增量检查、季度评审会前全量检查、撤销条件疑似触发时针对性检查。
- 工程成熟团队可把状态一致性检查（改状态未改索引则 CI 告警）、撤销条件监控、过期提醒嵌入 CI/CD。

## 红旗

**绝不要：**
- 为易逆转 / 显而易见 / 无替代的决策写 ADR——泛滥即噪音，读者会不再信任任何 ADR
- 修改已 Accepted 的 ADR 来"更新"决策——应创建新 ADR 取代
- 省略撤销条件（五要素中最容易漏、也最重要）
- 用"选了什么"代替"为什么选、不选什么、何时重选"

## 底线

**ADR 记录的是当时语境下的决策理由。** 知识生命周期能否追上技术生命周期，取决于今天是否写下了"当时为什么只能这么选"。
