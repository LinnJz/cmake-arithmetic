三个月后有人问你"为什么用Redis不用Memcached"一一你记不清了。当时的选择基于什么因素一一你现在只能靠记忆回忆。而现在你的记忆跟当时的情况已经不一样了。这就是你的团队在重复争论同一个架构问题一一每18个月重新讨论一次一一因为没有人记录"为什么当时选了这个"。
每个架构决策都有两个生命周期：**技术生命周期**和**知识生命周期**。技术生命周期是"**这个方案能用多久**"一一通常取决于组件版本、业务规模、团队能力。知识生命周期是“**做出这个决定的理由能存活多久**"一一这个周期往往比技术生命周期短得多，而且结束得悄无声息：当做出决策的那个人离开团队、或记忆模糊的那一刻，知识周期就结束了。**技术周期结束意味着该换方案了，知识周期结束意味着团队开始无意识地重复过去的错误。**

# 不记录架构决策的四个代价

| 代价 | 表现 | 发生频率 |
|------|------|----------|
| **重复争论** | 每12-18个月重新讨论一次相同问题——"为什么不用Redis？""上次为什么没选微服务？"——因为没人记得当初的排除理由 | 每个团队每季度至少1次 |
| **新人盲区** | 新成员接手系统时面对一堆看不懂的选择——"为什么订单表在这里有个冗余字段？"——没有人能在合理时间内给出答案 | 每个新人入职后的前3个月 |
| **迁移瘫痪** | 当需要推翻某个早期决策时，团队无法评估"当时限制条件是否还在"，因为原始上下文已经丢失——最保险的做法是什么都不动 | 每次架构升级或技术替换 |
| **决策归因偏差** | 没有记录时，团队倾向于用当前的结果反推当时的动机——成功的技术选型被神化为"高瞻远瞩"，失败的被贬低为"当时就这么傻"——但真实情况往往是：当时的约束决定了一切 | 每次复盘和AAR（After Action Review） |

这些代价的共同根源是：**人脑不适合长期存储带有当时约束条件的决策理由**。我们擅长记住"选了什么”，但很容易忘记"当时为什么只能这么选"。而"为什么只能这么选"恰恰是未来做反向决策时最需要的信息一一当你想推翻一个旧决策时，你需要知道当年的前提条件是否还在。
ADR（Architecture Decision Record）解决的就是这个问题。不是记录"用了什么技术"—一是记录**为什么做这个选择、考虑了什么替代方案、什么条件下会重新考虑[**1]。让知识生命周期追上甚至超越技术生命周期。

# ADR 五要素

| 要素         | 内容                                             |
| ------------ | ------------------------------------------------ |
| **背景**     | 当时的技术情况和约束——团队规模、技术栈、时间压力 |
| **决策**     | 具体做了哪个技术选择                             |
| **后果**     | 这个选择带来了什么影响——好的和坏的               |
| **替代方案** | 当时还考虑了哪些选择——以及为什么不选             |
| **撤销条件** | 什么情况下会重新考虑并选择替代方案               |

最容易漏但最重要的是“撤销条件"——它定义了"这不是永久决定——这是基于当时判断的最优选择。如果条件变了——我们要重新考虑它"。这让ADR成为了**可以过期的、基于信息的合理选择**——而不是"刻在石头上的决定"。

# 详细的ADR结构与模板

一个完整的ADR通常包含以下字段，使用Markdown格式存储在代码仓库中：

- 选用了具体的组件/版本
- 使用的具体方式
- 不做的范围界定

## 后果
正面：
- {正面影响1}
- {正面影响2}

负面：
- {负面影响1}
- {负面影响2}

# ADR案例：信贷系统引入规则引擎

以下是一个完整的ADR示例，展示金融信贷业务场景下实际落地时的样子：

```
# ADR-001：信贷审批系统引入Drools规则引擎解耦风控策略

- **状态**： Accepted
- **日期**： 2025-06-01
- **作者**： 信贷风控技术团队
- **最后修改**： 2025-06-15

## 上下文
信贷审批系统每天处理约10万笔进件。风控团队每个月调整3-5次审批规则（额度计算、黑名单匹配、多头借贷判断），每次修改都需要开发团队排期发布，平均交付周期3-5天。同时，随着合规要求收紧（如反洗钱新规），审批规则从30条膨胀到120条，硬编码的if-else分支逻辑已经难以维护，一条规则修改经常导致其他规则的意外触发。

约束条件：系统每日在线处理贷款申请，不允许停机迁移；风控团队以业务人员为主，不具备Java编码能力；存量审批逻辑覆盖8个信贷产品，每个产品的额度计算规则不同。

## 决策
引入Drools规则引擎，将风控审批策略从Java代码中剥离为独立的决策表（DecisionTable）和DRL规则文件。风控团队通过规则管理系统（RMS）上传Excel决策表，无需开发团队介入即可上线策略变更。

## 后果
正面：
- 风控规则修改周期从3-5天缩短到2小时内完成（从上传到生效）
- 规则条数从120条增长到350条，维护成本未显著增加
- 审批逻辑对业务人员透明化，风控团队可在沙箱环境中预览规则变更的影响范围

负面：
- 规则引擎引入约8ms的额外推理延迟，需要增加缓存层补偿
- Drools规则的回滚机制不完善，紧急回退时需依赖版本控制系统
- 部分极简规则（如"年龄<18拒绝"）使用规则引擎反而比if-else更重，存在过度工程风险

## 替代方案
方案A：继续维护硬编码if-else。不选原因：对开发团队负担可控，但风控团队的策略变更完全依赖开发排期，单次紧急合规调整在业务上不可接受。

方案B：自建轻量级规则框架。不选原因：灵活性最高，但团队没有规则引擎领域经验，自建质量风险高，且后续维护成本不可预测。

方案C：迁移到第三方风控SaaS。不选原因：对接成本最低，但核心审批逻辑依赖外部厂商，数据合规（信贷数据不出域）不满足金融监管要求。

## 撤销条件
当以下条件出现时，应重新评估此决策：
- 风控规则条数回落到50条以下（业务萎缩或产品线缩减）
- Drools版本停产或社区停止维护
- 监管要求审批逻辑必须使用特定第三方系统
- 规则执行延迟超过50ms且无法通过缓存优化解决

## 变更历史
| 日期 | 变更类型 | 原因 | 操作人 |
|------|---------|------|--------|
| 2025-06-01 | 创建 | 首次编写 | 张工（架构组） |
| 2025-06-15 | 更新 | 补充回滚机制和缓存补偿方案 | 王工（风控技术） |
```

# ADR的维护与管理

## 生命周期

ADR不是写一次就结束的静态文档，它有完整的生命周期：

```
Proposed（提议中）→Accepted（已接受）→Deprecated（已弃用）
                                    ↓
                                    Superseded（被取代）
```

* Proposed：初稿，团队仍在讨论
* Accepted：团队达成共识，开始实施
* Deprecated：决策已不再适用，但没有被特定新决策替代
* Superseded：被新的ADR明确取代，新旧ADR之间要互相引用

## 不可变原则

一旦ADR被接受并合并到仓库，就**不应该再修改**（除修正拼写错误外）。ADR是"历史快照"一一它记录的是当时语境下的决策理由。如果架构发生变化，应当创建一份**新的ADR**来取代旧的，而不是在原ADR上改。旧ADR保留作为历史记录。

## 版本间的关联管理

当一份ADR被取代时，新旧ADR之间需要建立双向引用：

```
旧ADR最后一行：
##被取代
本决策已被 ADR-008 取代

新ADR第一行：
##取代
本决策取代 ADR-001
```

这种双向引用确保了架构决策的可追溯性。任何人在阅读旧ADR时都能快速找到当前生效的决策。

## 定期审查机制

建议每6-12个月对ADR进行一轮审查。审查时关注：

1. 撤销条件是否已经被触发
2. 业务规模是否已超出ADR假设的范围
3. 技术栈版本是否已有重大更新
4. 团队规模或组织结构是否已有变化

审查结果可以是：保持有效、标记为Deprecated、或创建新的ADR来**Supersede**旧决策。可以使用定时任务或CI/CD流水线中的checklist来触发定期审查

# ADR的状态跟踪一一从单点记录到全局可见

ADR不是写完就结束的静态文档。当团队积累到10份以上ADR时，如果没有全局状态跟踪，就会出现"ADR目录里一堆文件，但没人知道当前哪些决策仍然有效、哪些已经过时“的局面。状态跟踪要解决的核心问题是：**一眼看清所有决策的当前状态**。

## ADR状态看板

推荐在`docs/adr/README.md`中维护一张**ADR状态矩阵**，作为团队架构决策的全局地图：

```
# ADR索引（最后更新：2025-09-15）

| 编号 | 标题 | 状态 | 决策日期 | 决策者 | 取代关系 |
|------|------|------|----------|--------|----------|
| ADR-001 | 订单系统引入RocketMQ | ✔️ Accepted | 2025-06-01 | 订单技术团队 | → ADR-008 |
| ADR-002 | 选用PostgreSQL为主数据库 | ✔️ Accepted | 2025-06-15 | 架构组 | － |
| ADR-003 | API统一走gRPC | ❌ Deprecated | 2025-07-01 | API团队 | － |
| ADR-004 | 缓存层引入Redis集群 | ⚠️ Proposed | 2025-08-20 | 支付团队 | － |
| ADR-005 | 日志收集从EFK迁移到Loki | 🔚 Superseded | 2025-07-10 | 运维团队 | → ADR-009 |

**状态说明**：
- ⚠️ Proposed – 正在讨论，尚未决策
- ✔️ Accepted – 已通过，正在或已经实施
- ❌ Deprecated – 已弃用，不再推荐使用
- 🔚 Superseded – 已被取代，查阅取代它的ADR
```

这张表格的价值在于：**任何人打开ADR目录的首页，就能在30秒内了解整个系统的架构决策全景**。新成员onboarding时可以优先阅读所有✔️ Accepted 状态的ADR，跳过❌和🔚的。

## 状态变更的日志化

ADR的状态不是一次定终身一一决策会过时、会被取代、会被弃用。每一次状态变更都应该被记录。在之前的基础模板中，我们已经将**变更历史**作为ADR的固定章节内置进去了一一这意味着每份ADR从创建之初就自带一张变更日志表。变更历史表推荐包含以下列：

| 日期       | 变更类型     | 原因                                   | 操作人         |
| ---------- | ------------ | -------------------------------------- | -------------- |
| 2025-06-01 | 创建         | 首次编写                               | 张工（架构组） |
| 2025-12-15 | 状态变更     | Accepted → Superseded，被 ADR-008 取代 | 李工           |
| 2026-01-10 | 撤销条件更新 | 增加“规则延迟超过50ms”条件             | 张工           |

状态变更日志的价值体现在两个场景：

* **审计追溯**：半年后复盘时，你能回答"这个决策什么时候失效的、为什么失效的、谁决定的失效"。没有日志的话，你只能猜测。
* **失效模式分析**：如果多个ADR的失效原因都是"业务规模超出预期"——这就是一个系统性信号，说明团队的架构决策普遍对规模增长估计不足。这个信号只有在你记录了“失效原因"之后才能被发现。

## 用AI做ADR状态审计

AI可以定期对ADR目录做状态审计。将当前所有ADR的文本输入AI，要求它：

```
请对当前ADR目录做状态审计：
1．检查是否有已过时但未被标记为Deprecated/Superseded的ADR
2．检查是否有多个ADR之间存在未记录的冲突或重叠
3．对比各ADR的撤销条件，标记已被触发的撤销条件
4．生成一份"状态异常ADR清单"——哪些ADR的状态需要更新但尚未更新
```

这种审计的频率建议每季度一次，触发条件可以是：新ADR创建时触发增量检查、季度架构评审会前触发全量检查、或某个ADR的撤销条件疑似触发时触发针对性检查。

## 状态跟踪的自动化

对于工程成熟度较高的团队，可以将ADR状态跟踪嵌入CI/CD流水线：

* **状态一致性检查**：PR中修改ADR状态时，自动检查是否同时更新了索引表。如果更新了ADR状态但没更新README，CI告警提示。
* **撤销条件监控**：将ADR的撤销条件（如"当P99延迟超过500ms"）接入监控系统。当指标触发条件时，自动在ADR上标记"撤销条件已触发，建议重新评估"。
* **过期提醒**：设定定期提醒机制一一每个ADR在达到审查周期（如6个月）时，自动在团队IM频道发送提醒："ADR-007距离上次审查已超过6个月，请安排审查。"

# ADR决策链一一追踪决策之间的依赖与演化

单个ADR记录了一个孤立决策的上下文。但真实系统的架构不是由单项决策构成的一一它是一个决策网络。选择用Kafka不是因为"Kafka好"，而是因为：之前选择了事件驱动架构（ADR-003）、然后又选择了异步库存扣减（ADR-001）、再选择了和已有消息中间件兼容的方案（ADR-007）。**这些决策之间存在因果链条**一一理解这个链条比理解单个决策更重要。

## ADR之间的四种关联关系

除了"Supersedes（取代）“之外，ADR之间还存在其他三种常见的关系。推荐在ADR文件的"参考"或新增的"关联ADR"字段中
明确标注：

| 关系类型          | 描述                               | 示例                                         | 标注方式                          |
| ----------------- | ---------------------------------- | -------------------------------------------- | --------------------------------- |
| Supersedes (取代) | 新决策替换了旧决策                 | ADR-008 取代 ADR-001                         | Depends on ADR-008（新ADR中标注） |
| Depends on (依赖) | 这个决策的成立依赖于另一个         | 选择Kafka的前提是选择了事件驱动架构          | Depends on ADR-003                |
| Refines (细化)    | 对高层决策做具体实现层面的决策     | 缓存策略的细化决策（本地缓存 vs 分布式缓存） | Refines ADR-002                   |
| Related to (关联) | 两个决策在同一个领域内但无直接依赖 | 消息队列选型和序列化协议选型                 | Related to ADR-006                |

标注方式示例：

```
## 关联ADR
- **Supersedes**：ADR-001（本决策取代了原有缓存选型决策）
- **Depends on**：ADR-003（事件驱动架构是使用Kafka的前提）
- **Refines**：ADR-002（本决策细化了分布式缓存的具体实现方式）
- **Related to**：ADR-006（与序列化协议选型在同一领域，但无直接依赖）
```

对于**Supersedes**关系，还需在旧ADR中标注“被取代”链接，形成双向引用；对于**Depends on**，若被依赖的ADR状态变为Deprecated或Superseded，应触发本决策的重新评估。

## 决策链的可视化

当ADR数量超过20份时，推荐使用工具生成决策关系图（如Mermaid、Graphviz），将Supersedes、Depends on等关系绘制为有向图，便于团队直观理解架构演进的脉络。示例Mermaid代码：

```Mermaid
graph LR
  ADR-003[事件驱动架构] -->|Depends on| ADR-008[选用Kafka]
  ADR-002[缓存策略] -->|Refines| ADR-004[Redis集群]
  ADR-001[旧缓存选型] -->|Superseded by| ADR-004
```

此图可放在`docs/adr/README.md`中，随ADR更新而更新。

## 结语

架构决策不是一次性的“选型记录”，而是团队集体智慧的**可追溯资产**。ADR让“为什么”不再依赖记忆，让每一次讨论都能站在前人的肩膀上，而非原地踏步。**建立记录习惯只需一次，而它的回报会持续到系统退役的那一天。**

从今天开始，为下一个关键决策写一份ADR。三个月后，你的团队会感谢你。
