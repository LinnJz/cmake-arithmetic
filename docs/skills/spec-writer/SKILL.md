# SPEC 撰写（spec-writer）

## 定位：SPEC 在四者关系中的位置

SPEC 是 PRD（为什么做）、ADR（怎么做）、SPEC（具体长什么样）、PLAN（什么时候交付）中的第三级——**被 ADR 约束过的 PRD 的可执行投影**。它的质量取决于两个承接口：

| 接口 | SPEC 的动作 | 反例（不该做） |
|------|-------------|----------------|
| 承接 PRD | 每条需求 → 可执行契约，标注溯源（需求-约束映射表） | 重述痛点、业务价值、功能列表 |
| 投影 ADR | 只写选型落地后的形态（如"OAuth2.0"→ `POST /auth/wechat` 字段） | 重抄 ADR 的上下文、替代方案、撤销条件 |
| 喂养 PLAN | 粒度细到能直接拆 WBS、估工时（WBS 输入表） | 混入里程碑、排期、资源分配 |

**明确不属于 SPEC**：PRD 的痛点与业务目标（prd-writer）、ADR 的权衡理由与撤销条件（adr-writer）、PLAN 的排期与资源（计划制定）。

## 核心规则

1. **可验证优先**：每条内容要么是可验证契约，要么是契约的支撑信息。写不出断言的描述 = 还没想清楚，回到需求澄清。
2. **无孤儿**：每条契约可溯源到 PRD 需求号，并标注依赖的 ADR。
3. **无重复**：不重述 PRD 的痛点与 ADR 的权衡理由。
4. **无占位符**：禁止"待定 / TBD / 视情况而定 / 处理好异常 / 类似上一节"。
5. **渐进严格（Progressive Rigor）**：低风险局部变更用精简规格；跨边界、契约破坏、迁移重、安全敏感用完整规格（判断表见 `references/contracts-guide.md`）。
6. **行为优先，实现不泄漏**：外部可验证行为进 SPEC；具体库/类/函数结构、文件路径进设计附注供 PLAN 参考，不进行为契约。

## 工作流

### Phase 0：输入检查（溯源门）

1. 读取已确认的 PRD（或需求描述），提取需求清单并编号（R1、R2…）。
2. 读取相关 ADR，提取决策约束（选型 → 契约须符合的字段/形态）。
3. 若仓库有领域词汇表或 CONTEXT.md，复用其术语，不另造词。
4. 若 PRD 或 ADR 缺失：提示先用 `prd-writer` / `adr-writer` 补齐，不凭空编造输入。
5. 输出「需求-约束映射表」：每条需求受哪些 ADR 约束。

### Phase 1：范围确认（对齐门）

1. 按渐进严格原则判断哪些需求需要完整 SPEC、哪些保持精简。
2. 识别契约面：接口 / 数据 / 状态 / 边界（错误与异常）。
3. 收集开放问题（Open Questions）：写 SPEC 时可能发现 ADR 撑不住预估场景——这是"SPEC 反推 ADR"回流，先登记，不擅改架构。
4. 与用户确认范围与开放问题后进入撰写。未确认前不输出完整 SPEC。

### Phase 2：撰写 SPEC

加载 `references/spec-template.md` 按结构撰写，写法要点：

- 行为契约用 `### Requirement:` + `#### Scenario:` + **GIVEN/WHEN/THEN/AND**，行为优先、可验证。
- 接口契约：方法/路径、入参、出参、错误码，标注兼容性。
- 数据契约：字段、类型、可空、索引、迁移影响。
- 状态机：状态、进入条件、退出条件、用户可见表现；无状态组件显式声明。
- 错误矩阵 + 边界条件：每个失败/边界场景一行（空数据/超时/并发/重复/非法输入/下游不可用/权限）。
- 验证锚点：每个契约映射一条 AC（ID/描述/测试类型/前置/期望结果），确定性通过/失败。
- Good/Base/Bad 用例：至少一组，Bad 含 Wrong vs Correct 反例。

细节写法见 `references/contracts-guide.md`。

### Phase 3：自检

加载 `references/checklist.md` 逐项检查三条验收标准：**无孤儿 / 无重复 / 可估时且可验证**。发现问题就地修复，修复后不重复走查。

### Phase 4：交付与对接

1. **落盘**：用 `scripts/new-spec.ps1` 生成 `docs/specs/NNNN-{slug}.md`（目录懒创建）。
2. **对接 PLAN**：确保 WBS 输入表已填（接口数/表数/状态数/AC 数/迁移项/估算建议），计划制定无需二次解读即可拆任务。
3. **对接 ADR 回流**：开放问题中需要新架构决策的，登记后提示用 `adr-writer` 新建 ADR。
4. **对接测试**：AC 表即测试用例输入，可直接交测试团队或用于验收。

## 红线

- 把 ADR 的 Options / 撤销条件 / 权衡理由抄进 SPEC。
- 重述 PRD 的痛点与业务价值。
- 写"处理好异常 / 加校验 / 补边界"而不给具体矩阵或条件。
- 用"类似前面需求"代替完整契约。
- 编造溯源：没有 PRD 需求支撑的契约条目（孤儿）。
- 编写无法验证的行为描述。

## 底线

**SPEC 是被 ADR 约束过的 PRD 的可执行投影**：它回答"确切是什么、怎么验证"，让 PLAN 无需二次解读即可拆解任务。溯源保证不丢需求，验证锚点保证不空转。
