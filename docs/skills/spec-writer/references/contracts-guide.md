# 契约写法细则

本文件说明 SPEC 各章节的写法要点与判断标准。写 SPEC 前阅读。

## 1. 行为契约写法（Requirement / Scenario）

- 每条需求用三级标题 `### Requirement: {名称}`，名称 < 50 字符、描述性强、**全局唯一**——它同时是变更追踪时程序化匹配的标识。
- 紧跟一句 SHALL 语句：`系统 SHALL {行为}` / `系统 MUST {行为}` / `系统 拒绝 {行为}`。
- 每个行为至少一个 `#### Scenario:`，步骤用加粗关键词：
  - **GIVEN** 前置状态（可选）
  - **WHEN** 触发条件
  - **THEN** 期望结果
  - **AND** 附加结果或约束
- 分支用子列表缩进保持层级；不要在场景里写"如果……则……"的长段落，拆成独立场景。
- **实现泄漏边界**：外部可验证行为进 SPEC；具体库/类/函数结构、执行机制、文件路径进设计附注（PLAN 参考用），不进行为契约。判断标准：能不能在没有实现细节的情况下照此写测试。

## 2. 接口契约写法

- 每条接口给出：方法 + 路径、Request 字段（名/类型/约束）、Response 字段（名/类型/约束）、错误码清单。
- 错误码与「错误矩阵」保持一致：同一种失败条件只能有一个错误码，全文档不得出现同码异义。
- 标注兼容性：新增字段（向后兼容）vs 破坏性变更（需进 ADR/变更评审）。
- 异步事件写明 Topic、Payload、Producer、Consumers——PLAN 据此拆联调任务。

## 3. 数据契约写法

- 每个表/实体给字段表：字段、类型、可空、索引、说明。唯一索引、联合索引单独标注用途。
- 变更表必须写明迁移影响：新增表（非破坏）/ 加字段（默认值？）/ 改约束（回填？）/ 删除列（数据保留策略）。
- 写清楚主数据流：数据从哪来、经过哪几层、落到哪，供 PLAN 评估联调与数据迁移工作量。

## 4. 状态机写法

- 无状态组件必须显式写"无状态"，避免 PLAN 误判复杂度。
- 每个状态给：进入条件、退出条件、用户/调用方可见表现。悬空状态（只进不出）是必查缺陷。
- 状态转换若涉及跨服务（如支付回调），把触发方写进「接口契约」或「数据契约」建立交叉引用。

## 5. 错误矩阵与边界条件

覆盖以下七类场景，缺一不可：
1. **空数据**：无记录 / 无返回时行为
2. **超时**：调用下游超过阈值
3. **并发**：同请求重复 / 同资源竞争
4. **重复**：幂等性要求
5. **超长 / 非法输入**：校验边界
6. **下游不可用**：依赖服务挂掉
7. **权限**：未登录 / 越权

每行 = 场景 | 触发条件 | 处理方式 | 用户/调用方反馈。禁止只写"做好异常处理/补全校验"这类占位。

## 6. 验证锚点写法（AC）

- 每条 AC 必须是确定性通过/失败：期望结果要可被命令或观测判定，禁止"工作正常/表现符合预期"。
- 若某条行为写不出 AC，说明该行为尚未被规格清楚——回到 Phase 1 与用户澄清，不要硬写。
- AC 引用测试类型：`API` / `UI` / `Logic`，与测试执行方式一一对应。
- AC ID 连续编号，不得跳跃。PLAN 的测试任务直接引用 AC ID。

## 7. Good / Base / Bad 用例

- **Good**：正常路径，一个典型输入。
- **Base**：边界路径，恰好卡在阈值/限制处的输入（如 TTL 临界、长度上限）。
- **Bad**：异常路径，非法/过期/缺失输入。
- 至少一组正例 + 一组反例（Wrong vs Correct），反例必须写明"为什么错、正确的做法是什么"。

## 8. 渐进严格（Progressive Rigor）判断

| 变更类型 | 规格深度 |
|----------|----------|
| 本地、低风险、单模块 | 精简：行为契约 + AC 即可 |
| 跨模块 / 跨仓库 | 完整：接口 + 数据 + 状态机 + 边界 |
| 契约破坏 / API 变更 | 完整 + 兼容性说明 + 迁移 |
| 迁移重 / 数据回填 | 完整 + 迁移影响专节 |
| 安全 / 合规敏感 | 完整 + 权限矩阵 + 审计点 |

## 9. 词汇纪律

- 复用仓库领域词汇表 / CONTEXT.md 的术语，不另造同义词。
- 同一个对象全文档用一个名字（会话就是会话，不一会 session 一会 会话）。
- 术语首次出现给出定义；定义变化视为契约变更，走变更历史。

## 10. 反模式速查（禁止）

- 把 ADR 的 Options/撤销条件/权衡理由抄进 SPEC。
- 重述 PRD 的痛点、业务价值、功能列表。
- 写"待定 / TBD / 视情况而定 / 后续补充"。
- 写"处理好异常 / 加校验 / 处理边界"而不给具体矩阵或条件。
- 用"类似前面需求"代替完整契约。
- 编造溯源：没有对应 PRD 需求的契约条目 = 孤儿，要么补需求，要么删条目。
