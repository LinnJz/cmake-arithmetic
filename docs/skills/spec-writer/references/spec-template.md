## 5. 状态机（有状态时必写，无状态则写明"无状态"）

| 状态 | 进入条件 | 退出条件 | 用户可见表现 |
|------|----------|----------|--------------|
| ANONYMOUS | 初始 | 登录成功 | 未登录 |
| ACTIVE | 登录成功 | 过期/登出 | 已登录 |
| EXPIRED | expires_at 到达 | 重新登录 | 会话失效 |

---

## 6. 错误矩阵与边界条件（必写）

"处理好异常"不是 SPEC，异常矩阵才是。每个失败/边界场景一行。

| 场景 | 触发条件 | 处理方式 | 用户/调用方反馈 |
|------|----------|----------|------------------|
| 授权码无效 | code 过期或伪造 | 拒绝并记录 | 401 INVALID_CODE |
| 并发重复提交 | 同一 code 双请求 | 幂等处理，仅建一会话 | 第二次复用首次结果 |
| 限流 | 超阈值 | 拒绝 | 429 RATE_LIMITED |
| 空数据 | 无会话记录 | 返回空态 | 未登录引导 |

边界条件至少覆盖：空数据、超时、并发、重复、超长、非法输入、下游不可用。

---

## 7. 验证锚点（必写）

每条行为契约至少映射一条验收标准（AC）。PLAN 的测试任务与 QA 验收以此为输入。

| AC ID | 对应需求/契约 | 描述 | 测试类型 | 前置条件 | 期望结果 |
|-------|---------------|------|----------|----------|----------|
| AC-001 | R1 / 接口 | 有效 code 换取会话 | API | 有效 code | 200 + token 字段齐全 |
| AC-002 | R1 / 行为 | 无效 code 被拒 | API | 伪造 code | 401 INVALID_CODE |
| AC-003 | R3 / 边界 | 超频被限流 | API | 已触发阈值 | 429 RATE_LIMITED |

测试类型取值：`API`（接口调用）/ `UI`（界面交互）/ `Logic`（纯逻辑）。期望结果必须是确定性的通过/失败判定。

---

## 8. Good / Base / Bad 用例（必写，至少一组）

| 类型 | 场景 | 输入 | 期望输出 |
|------|------|------|----------|
| Good | 正常登录 | 有效 code | 200 + 会话 |
| Base | 边界登录 | 恰好到达 TTL 前 | 200 且会话可刷新 |
| Bad | 异常登录 | 过期 code | 401，无会话落库 |

## 9. 开放问题（必写）

写 SPEC 时发现 ADR 撑不住预估场景（并发超限、性能不达标）——登记在此，是"SPEC 反推 ADR"的回流触发器。需新架构决策的问题，用 adr-writer 新建 ADR。

- [ ] {问题} — 需在实现前决策；影响：{若不解决会怎样}
- [ ] {问题} — 已触发 adr-writer 回流，ADR 待建

如无：写"无开放问题。SPEC 可直接进入 PLAN 制定。"
