# 调试技术参考

## 1. 根因回溯（Root Cause Tracing）

**何时用**：错误在调用栈深处、无效数据来源不明、堆栈显示长调用链。

核心：从症状点沿调用链**向后**追溯，直到找到原始触发者，修源头而非症状点。

过程：

1. 观察症状（错误信息 + 位置）。
2. 找直接原因：哪行代码直接造成它？
3. 问"谁调用了我"：回溯调用方。
4. 继续向上：传进来的值是什么？值从哪来？
5. 找到原始触发点：坏值最早从哪产生？
6. 在源头修复。

无法手工追踪时加插桩：

- 在危险操作**之前**记录上下文（目录、cwd、环境变量、时间戳）——失败后记录为时已晚。
- 捕获完整调用链：`new Error().stack`（TS/JS）、`System.Environment.StackTrace`（.NET）、`traceback.format_stack()`（Python）、调试器 backtrace。
- 测试环境用直接输出（如 `console.error`）而非 logger——logger 可能被抑制。

**定位"污染源"测试**：若测试期间产生副作用但不知是哪个测试干的，用二分——逐测试运行，停到第一个污染者。

## 2. 组件边界取证（Multi-Component Evidence）

**何时用**：多组件链（CI→构建→签名、API→服务→数据库）中不知哪一环失败。

在**每个**组件边界记录：数据进入什么、离开什么、环境/配置是否传播、各层状态。运行一次拿到证据，定位失败组件，再深挖该组件。

示例（多环节系统）：

```
环节1: 工作流        echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"
环节2: 构建脚本      env | grep IDENTITY
环节3: 签名环节      检查密钥链状态
环节4: 实际签名      带 -v 运行并看哪一步报错
```

这揭示具体哪一层失败（工作流✓→构建✗），从而锁定侦查范围，避免猜。

## 3. 防御纵深（Defense-in-Depth）

**何时用**：修复了由非法数据导致的 bug 之后。单点校验会被其他代码路径、重构或 mock 绕过。

> **单一校验 = "我们修好了 bug"；多层校验 = "我们让 bug 不可能发生"。**

四层（从入口到兜底）：

1. **入口校验**：API 边界拒绝明显非法输入（非空、存在、类型正确）。
2. **业务逻辑校验**：确保数据对该操作有意义。
3. **环境守卫**：特定上下文禁止危险操作（如测试环境拒绝在临时目录之外写文件）。
4. **调试插桩**：操作前记录上下文，为其他层失效时保留取证现场。

应用：① 追踪数据流——坏值从哪产生、经哪使用；② 列出所有经过的检查点；③ 逐层加校验；④ 逐层测试——试着绕过第一层，验证第二层能接住。

实践表明四层各有捕获，缺一不可：不同代码路径绕过入口校验、mock 绕过业务检查、跨平台边界需要环境守卫、调试插桩识别结构性误用。

## 4. 条件等待（Condition-Based Waiting）

**何时用**：测试用任意延迟（setTimeout/sleep）而 flaky；并行下超时；等待异步完成。

核心：等待**关心的实际条件**，而非猜测耗时。

```
❌ await sleep(50ms); expect(getResult()).toBeDefined()
✅ await waitFor(() => getResult() !== undefined)
```

通用轮询实现要点：每 10ms 轮询（1ms 空转浪费 CPU）；必须带超时与清晰报错；循环内调用 getter 取新值（勿缓存旧状态）。

**何时任意超时是正确的**：先等待触发条件，再基于已知时序（如工具每 100ms 跳动一次、需要 2 个 tick）等固定时长，并注释 WHY。不允许凭空猜测的 sleep。

## 5. 二分（Bisection）

**何时用**：bug 出现在两个已知状态（commit、数据集、版本、配置）之间。

自动化：`git bisect start` + `git bisect run <脚本>`——脚本在状态 X 下构建并运行回路，非零退出表示失败。数据集/配置二分同理，替换脚本输入即可。

**非确定性复现不要二分**：先提升复现率再二分，否则二分结果噪声不可信。
