# 诊断（Diagnose）

面向顽固 bug 与性能回归的多语言调试纪律，适用于 C/C++、Rust、Java、.NET、Python、JS/TS。共六个阶段，仅在明确说明理由时跳级。

## 核心信条

1. **先建反馈回路，再谈根因。** 没有快速、确定性、可自动运行的 pass/fail 信号，看再多代码也找不到原因；有了它，二分、假设检验、插桩都只是消耗这个信号。
2. **无根因不修复（铁律）。** 症状修复即失败。未完成根因调查前不得提出修复方案。
3. **修复的价值不在修好这个 bug，而在让这一类 bug 不再发生。** 复盘与知识沉淀是流程的一部分，不是可选项。

## Phase 1 — 构建反馈回路（投入最大精力）

**这是本 skill 的核心，其余全是机械执行。** 回路越快的确定性循环越接近调试超能力。

按大致顺序尝试构造 pass/fail 信号：

1. **失败测试** — 在能触达 bug 的接缝处写单元/集成/e2e 测试。
2. **Curl/HTTP 脚本** — 针对运行中的 dev server。
3. **CLI 调用 + 快照** — fixture 输入，stdout 与已知正确快照 diff。
4. **无头浏览器**（Playwright/Puppeteer）— 驱动 UI，断言 DOM/console/network。
5. **回放捕获的 trace** — 把真实请求/载荷/事件日志落盘，隔离重放。
6. **一次性 harness** — 最小化子系统（单服务、mock 依赖）单函数调用触发 bug 路径。
7. **属性/模糊测试** — 若 bug 是"偶发错误输出"，跑 1000 个随机输入找失败模式。
8. **二分 harness** — bug 出现在两个已知状态（commit/数据集/版本）之间时，自动化 `git bisect run`。
9. **差分循环** — 同一输入跑旧版 vs 新版（或两套配置），diff 输出。
10. **HITL 脚本** — 兜底。必须人工点击时，用 `scripts/hitl-loop.ps1` 驱动对方，让循环保持结构化。

**迭代回路本身**：建好回路后追问——能否更快（缓存 setup、跳过无关初始化、缩小范围）？信号能否更锐（断言具体症状，而非"没崩"）？能否更确定（锁定时间、seed RNG、隔离文件系统、冻结网络）？30 秒的 flaky 回路 ≈ 没有回路。

**非确定性 bug**：目标不是干净复现而是**更高复现率**。触发循环 100 次、并行化、加压力、缩时序窗、注入 sleep。50% 复现率可调试，1% 不可——持续提升到可调试。

**确实无法构建回路时**：停下来明说。列出已尝试的方法，向用户索要：(a) 能复现的环境访问权，(b) 捕获的工件（HAR、日志转储、core dump、带时间戳的录屏），或 (c) 临时生产插桩许可。**没有回路就不得进入假设阶段。**

## Phase 2 — 复现与症状捕获

跑回路，看 bug 出现，然后确认：

- [ ] 复现的是**用户描述**的失败模式，而非邻近的另一个失败。修错 bug = 修错。
- [ ] 多次运行可复现（非确定性 bug 至少达到可调试的复现率）。
- [ ] 已捕获精确症状（错误信息、错误输出、耗时），供后续验证修复对症。
- [ ] 已完整读错误信息与堆栈（不跳过任何行），记录行号、文件路径、错误码。
- [ ] 已检查最近改动（`git diff`、近期 commit、新依赖、配置变更、环境差异）。

## Phase 3 — 根因调查与可证伪假设

**先取证，后假设：**

**多组件系统**：在**每个组件边界**加诊断插桩（记录进入什么、离开什么、验证环境/配置传播、检查各层状态），运行一次定位失败的组件，再深挖该组件。不要直接猜。

**错误在调用栈深处**：向后**追踪数据流**找原始触发点（见 `references/techniques.md` 根因回溯），修源头而非症状点。

**模式分析**：找同代码库中相似的可工作代码，完整阅读参考实现，列出与坏代码的**每一个**差异（别假设"这不可能有影响"），弄清依赖与前置条件。

**然后生成 3–5 条排序假设，每条必须可证伪**：

> 格式："如果 X 是原因，那么改 Y 会让 bug 消失 / 改 Z 会让它更糟。"

无法陈述预测的假设只是直觉——丢弃或打磨它。**测试前把排序列表展示给用户**（领域知识可能秒级重排，或直接排除已试过的）；用户不在线则不阻塞，按自己排序继续。

## Phase 4 — 插桩验证（一次一变量）

- 每个探针必须对应 Phase 3 的具体预测，**一次只改一个变量**。
- 工具偏好：① 调试器/REPL 断点（一个断点胜过十条日志）→ ② 在能区分假设的边界加定向日志 → ③ 绝不"全量打日志再 grep"。
- 每条调试日志打**唯一前缀** `[DEBUG-a4f2]`——收尾时一个 grep 全清。带标签的日志会死，无标签的会存活。
- 假设被证伪就形成新假设，不要叠修复。承认"我不知道"，不假装懂。
- **性能分支**：性能回归用日志通常是错的。先建立基线测量（计时 harness、剖析器、查询计划），再二分。**先测量，后修复。**
- 时序/环境相关失败：参考 `references/techniques.md` 的条件等待与确定性化手法。

## Phase 5 — 修复与回归测试

回归测试**先于修复**，但只在存在**正确接缝**时写——接缝必须能按调用点的真实 bug 模式复现问题。接缝太浅（单一调用方测试、无法复现触发链的单元测试）只会给出虚假信心。

**若无正确接缝，这本身就是发现**：架构阻碍了 bug 的锁定。记录它，标注给复盘阶段。

存在正确接缝时：

1. 把最小复现转成该接缝处的失败测试。
2. 看它失败。
3. 应用修复——修根因不修症状，**单个**修复，不做"顺手"重构。
4. 看它通过。
5. 用 Phase 1 回路重跑原始（未最小化的）场景。
6. **防御纵深**：修复后考虑在数据流经的每一层加校验，使 bug 在结构上不可能（见 `references/techniques.md`）。

**3 次以上修复失败**：STOP，质疑架构本身，与用户讨论后再继续。这不是假设失败，是错误架构。

## Phase 6 — 清理与复盘（打破修复-遗忘循环）

声明完成前必须满足：

- [ ] 原始复现不再出现（重跑 Phase 1 回路）。
- [ ] 回归测试通过（或接缝缺失已记录）。
- [ ] 所有 `[DEBUG-...]` 插桩已移除（grep 前缀）。
- [ ] 一次性原型已删除（或移至明确标记的调试位置）。
- [ ] 正确的假设已写入 commit/PR 说明，供下一位调试者学习。

**然后从五个维度复盘**，把结论沉淀到仓库文档（spec/ADR/指南），而非留在聊天里——留在对话里的分析一文不值：

1. **根因分类**：A 缺规格 / B 跨层契约 / C 变更传播遗漏 / D 测试覆盖缺口 / E 隐式假设。
2. **修复为何失败**：表面修复 / 范围不全 / 工具局限 / 心智模型局限（只在同一层找）。
3. **预防机制**：文档化、架构使其不可能、编译期约束、运行时监控、测试覆盖、评审清单。
4. **系统性扩展**：还有哪里可能存在同类问题？是否存在设计缺陷 / 流程缺陷 / 知识缺口？
5. **知识沉淀**：更新指南/文档、建 issue/工单、更新相关 check。

若复盘答案涉及架构性改动（无好的测试接缝、调用方纠缠、隐藏耦合），带具体证据转交架构类 skill 处理。**建议在修复落地之后提出**——此刻掌握的信息比开始时更多。

## 红旗（出现即 STOP，回 Phase 1）

- "先快速修一下，回头再查"
- "试一下改 X 看行不行" / "大概就是 X，改它"
- 未追踪数据流就提修复方案
- 一次改多处 / 跳过测试手动验证
- 已试 2 次以上仍在"再试一次修复"
- 每次修复都在别处引出新问题（→ 架构问题）
