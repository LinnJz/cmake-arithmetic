# S5 测试：TDD 执行指南

开发自证阶段。写测试先行，看它失败，最小实现，看它通过。

## Iron Law

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

先写代码再补测试？删除重来。无例外。

## 核心原则

- 没看到测试失败，就不知道测试测对了东西。
- 测试后补的测试会立即通过，立即通过证明不了任何事——可能测错对象、可能测实现而非行为、可能漏掉你没想到的边界。

## 适用范围

- 必用：新功能、修 bug、重构、行为变更。
- 例外（先问用户）：一次性原型、生成代码、配置文件。
- "就这一次跳过 TDD"？那是合理化借口，停下。

## 循环：红绿重构

1. **RED 写失败测试**：一个测试只测一个行为，命名清晰，测真实代码（非不得已不用 mock）。
2. **Verify RED（必做）**：运行测试，确认：失败而非报错、失败原因符合预期（功能缺失而非笔误）。测试直接通过？你在测已有行为，改测试。报错？修错重跑直到正确失败。
3. **GREEN 最小实现**：最简代码让测试通过。不加功能、不顺手重构、不"优化"。
4. **Verify GREEN（必做）**：运行测试，确认：通过、其他测试仍通过、输出干净。
5. **REFACTOR**：只在绿灯后，去重、改名、抽函数。保持绿灯，不加行为。
6. 下一个失败测试，继续。

## 测试质量

| 质量 | 好 | 坏 |
|------|----|----|
| 最小 | 一个行为；名字里有"and"就拆开 | `test('validates email and domain')` |
| 清晰 | 名字描述行为 | `test('test1')` |
| 表达意图 | 展示期望的 API | 隐藏代码应做什么 |

## 反合理化

| 借口 | 现实 |
|------|------|
| 太简单不用测 | 简单代码照样坏；测试只要 30 秒 |
| 之后补测试 | 后补立即通过，证明不了任何事 |
| 手动测过了 | 手动无记录、不可重跑、压力下必漏 |
| 删掉 X 小时成果浪费 | 沉没成本；留着无法信任的代码才是技术债 |
| 保留当参考，先写测试 | 你一定会改它 = 变相后补。删除就是删除 |
| 需要先探索 | 可以。探索代码丢弃，重头走 TDD |
| TDD 太教条，要务实 | 测试先写才是务实：提交前抓 bug、防回归、文档化行为、放心重构 |
| 测试难写 = 设计难用 | 听测试的：难测 = 接口复杂，简化设计 |

## 红牌：停止并重来

- 代码先于测试
- 测试立即通过
- 说不出测试为什么失败
- "just this once"
- "已手动测过"
- "删掉太浪费"
- 以上任一出现 → 删代码，重头 TDD。

## 验证清单（S5 Gate 证据）

- [ ] 每个新函数/方法有测试
- [ ] 每个测试先看它失败，且失败原因正确
- [ ] 最小实现通过
- [ ] 全部测试通过，输出干净
- [ ] 当次运行输出作为 Gate 证据附上

缺一项 = 跳过了 TDD，重来。
