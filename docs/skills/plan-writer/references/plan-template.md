# PLAN 模板

在 Phase 3（计划评审对齐）前按本模板编制。全部小节均有说明；标「必写」的不可省略。

```markdown
# PLAN：{项目/能力名}

**文档信息**

| 版本 | 日期 | 作者 | 状态 |
|------|------|------|------|
| V1.0.0 | [当前日期] | [用户] | Draft |

**溯源**（必写——本计划在 PRD/ADR/SPEC/PLAN 链中的承接口）

| 上游文档 | 编号/版本 | 说明 |
|----------|-----------|------|
| PRD | [名称/版本] | 覆盖需求 R1-R5，范围冻结项 |
| ADR | ADR-0001, ADR-0003 | 决策约束：OAuth2.0 会话、Redis TTL |
| SPEC | SPEC-0001 | WBS 输入来源（接口/表/AC 数） |

**变更历史**

| 日期 | 变更 | 原因 | 操作人 |
|------|------|------|--------|
| [日期] | 创建 | 首次编写 |  |

---

## 1. 起点推断（必写）

扫描仓库已有产物，决定计划从哪个阶段开始（不全从 S1）：

| 已存在 | 结论 |
|--------|------|
| PRD ✓ / ADR ✓ / SPEC ✓ / AC ✓ | 从 S4 实施开始，省略上游文档阶段 |
| 仅 PRD ✓ | 从 S2 架构开始，S1 标记跳过 |
| 全部缺失 | 从 S1 开始，覆盖 PRD→ADR→SPEC→实施全程 |

判断依据：[实际扫描到的文件/链接，逐条列出]

## 2. 阶段表（必写——阶段线）

| 阶段 | 产出物 | 进入条件 | 退出条件（Gate） | 责任人 |
|------|--------|----------|------------------|--------|
| S0 计划编制 | 本计划 | SPEC 已确认 + WBS 输入齐 | 计划评审通过，与 PRD/ADR/SPEC 对齐 |  |
| S1 需求 | PRD | 计划已批 | PRD 评审通过，范围冻结 |  |
| S2 架构 | ADR | PRD 冻结 | ADR 评审通过（三条件门） |  |
| S3 规格 | SPEC | PRD+ADR 齐 | SPEC 自检通过（无孤儿/无重复/可验证） |  |
| S4 实施 | 代码 + coding-checklist 勾选 | 该阶段任务清单就绪 | 每任务验证锚点通过，产出可测 |  |
| S5 测试 | 测试结果 | 产出物进入测试 | 无 P0/P1 失败，证据留存 |  |
| S6 验证/验收 | 验收报告 | 测试通过 | 对照 SPEC 契约 + AC 全绿 |  |
| S7 质量门 | 自检 + Code Review 结论 | 验证通过 | 无 Critical/Important 遗留 |  |

被起点推断跳过的阶段在表格中整行标记 `已跳过（依据：见第 1 节）`，不删行、不填空。

## 3. 里程碑（必写）

| 里程碑 | 关联阶段 | 计划日期 | 外部依赖 | 缓冲 |
|--------|----------|----------|----------|------|
| M1 计划冻结 | S0 | [日期] | 无 | 0 |
| M2 规格齐备 | S3 | [日期] | [第三方接口交付] | [N] 天 |
| M3 联调通过 | S6 | [日期] | | [N] 天 |

## 4. WBS 任务分解（必写——喂执行）

每个任务：ID、关联阶段、关联 AC、coding-checklist 勾选项、估算。任务粒度 = 可独立验证的一步。

### Task T-001：[任务名]（阶段 S4，关联 AC-001）

- [ ] **步骤 1：[动作]**：[完整内容/命令，禁止占位符]
- [ ] **步骤 2：[动作]**：[完整内容/命令]
- [ ] **步骤 3：运行验证**
  运行：`{确切命令}`
  期望：`{确切输出或通过标准}`
- [ ] **步骤 4：提交**（如使用 VCS）
  运行：`{git add/commit 命令}`

### Task T-002：[任务名]（阶段 S5，关联 AC-002）
……

## 5. 风险与缓冲（必写——管理视角的核心）

| 风险 | 可能性 | 影响 | 应对 | 缓冲天数 |
|------|--------|------|------|----------|
| 外部依赖交付延迟 | 中 | 高：阻塞联调 | 提前联系、备选方案 | 2 |
| 新成员上手慢 | 低 | 中 | 文档先行、结对 | 1 |
| 并发量预估偏差 | 中 | 高：需要新增 ADR | 预留架构评审时间 | 3 |

## 6. 回流规则（必写——持续迭代的显式触发器）

| 触发条件 | 动作 |
|----------|------|
| 测试失败（P0/P1） | 回 S4/S5 修正 → 回归测试，不跳级 |
| 验证不通过（AC 红） | 回 SPEC 澄清契约 或 回实施修正 |
| 排期估算超限 | **PLAN 反推 PRD**：砍需求 → 更新 PRD → 同步 SPEC → 重新排期 |
| 写 SPEC 时发现 ADR 撑不住 | **SPEC 反推 ADR**：新建 ADR → 更新 SPEC → 回归 |
| Code Review 发现架构级问题 | 回 S2 重估，新增 ADR |
| 外部依赖延期 | 触发里程碑重排，更新缓冲 |

细则见 `references/gates-and-loops.md`。

## 7. 外部依赖清单（必写）

| 依赖 | 类型 | 交付时间 | 责任人/来源 |
|------|------|----------|-------------|
| 微信授权码接口 | 第三方 | [日期] | 微信开放平台 |
| 结算系统联调环境 | 内部 | [日期] | @xxx |

## 8. 交接约定（必写——贯穿机制）

- 每个 Gate 通过后更新 `handoff.md`（进度/未决事项/下一步）。
- 会话中断：读 `handoff.md` 即可无痛续跑。
- 任务完成：`handoff.md` 顶部标注 `[DONE]`，写最终结论。
```
