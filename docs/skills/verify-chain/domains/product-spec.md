# 领域配置：产品 PRD / 规格

## 验证对象

需求与实现的对应关系、字段定义、业务流程状态、约束条件、验收标准、范围边界。

## 触发示例

- "验证这份 PRD" / "核查需求覆盖是否完整"
- "这个字段在数据库里到底存不存在"

## 断言分类体系

| 类别 | 说明 | 示例问题 |
|------|------|---------|
| `Requirement` | 需求条目是否可落地、是否与已确认基线一致 | "该需求在当前迭代基线中是否存在？" |
| `FieldDef` | 字段名、类型、默认值、是否必填 | "`user.status` 的枚举值是否真的包含 `pending`？" |
| `FlowState` | 流程状态、状态机、转换条件 | "下单流程的状态机是否遗漏了"已取消"分支？" |
| `Constraint` | 性能、安全、合规等约束数值 | "并发上限 5000 是否与架构设计一致？" |
| `Acceptance` | 验收标准是否可度量、可测试 | "验收标准里的 '流畅' 是否有量化指标？" |
| `Gap` | 遗漏需求、边界、异常流、依赖 | "是否遗漏了支付超时回滚的需求？" |

## 权威来源白名单（按优先级）

1. 项目内部：已确认的需求基线、当前代码实现（接口/数据表/前端字段）
2. 关联文档：架构设计、接口文档、数据库设计、验收用例
3. 上游依赖：所引用外部系统的官方文档（作为契约）
4. 竞品对照 —— 仅作参考且必须标注来源

## 绝对禁止引用

- 未落地的讨论记录、个人猜测、二手转述（需求未确认前只能标 ❓）

## 搜索偏好

- **语言**：跟随项目（中文/英文皆可）
- **时效**：以当前迭代/当前分支代码为准
- **关键词策略**：仓库内代码检索优先；外部仅核对外部契约

## 修复策略备注

- 需求与实现不一致时，标注"基线版本 + 不一致点"，不擅自改需求口径
- 无法确认的实现细节标 ❓，注明"需向实现团队确认"
