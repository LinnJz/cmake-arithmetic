# 验证链（Verify Chain）

## 触发条件

当用户明确表示以下意图时调用此技能：
- "验证这篇文章"、"核查文章内容"、"check 文章"、"verify article"
- "检查有没有错误"、"帮我审稿"
- 对任意**可核查内容**提出验证需求，例如：
  - "验证这份 API 文档的参数行为"
  - "这份 PRD 的需求覆盖是否完整"
  - "核查这个科普/健康/财经数据"
  - "这个面试题的答案对不对"
  - "这串命令参数/配置文件能跑吗"
  - "这个代码示例能编译运行吗"
  - "核查译文是否引入事实错误"
  - "引用的法规/标准还有效吗"
- 用户提到 `/verify` 或 `/验证链`

## 领域选择

本技能面向**通用验证**，通过"领域配置"（`domains/` 目录）决定核查口径。执行第一步是确定领域：

1. **用户明确指定领域** → 直接使用（如 "用健康领域标准核查这篇文章"）
2. **用户未指定** → 根据内容形态自动判定：

| 内容形态 | 领域 |
|---------|------|
| IT 技术文章/教程/对比评测 | `tech-article` |
| API/三方库/框架文档 | `api-doc` |
| 需求/PRD/规格书 | `product-spec` |
| 科普、知识性内容 | `sci-pop` |
| 健康、医疗、养生内容 | `health-medical` |
| 财经、投资、经济数据 | `finance-econ` |
| 面试题、考试题库、习题解答 | `exam-qna` |
| 工具/软件操作手册 | `tool-doc` |
| 含可执行代码的教程/示例 | `code-example` |
| 翻译稿（中英互译等） | `translation` |
| 合规、法规、安全标准 | `compliance` |

3. **无法判定** → 默认 `tech-article`，并在报告中注明

领域配置定义了三件事：**断言分类**（Critic 用）、**权威来源白名单**（Verifier 用）、**修复策略**（Repairer 用）。它优先于通用 prompt。

## 不适用场景

- 纯理论/学术论文（需要专家同行评审，AI 无法替代）
- 非事实性内容（散文、小说、观点、影评）
- 纯个人经验分享（"我在项目中遇到的一个坑"——个人经历无法核查）
- 企业内部私有系统、闭源库/未公开硬件寄存器等无公开资料可对照的细节（此类断言通常只能标记 ❓，需人工确认）

## 执行流程

### 阶段 0：领域识别与配置加载

```
从 domains/ 选择领域配置；将配置内容注入后续各阶段
```

**执行方式**：串行。读取所选领域配置文件，其内容作为各阶段 prompt 的附录（优先级最高）。

### 阶段 1：Critic — 断言提取

```
使用 Critic System Prompt（prompts/critic.md）
附录：所选领域的断言分类体系
输入：完整原文 Markdown
输出：10-20 个关键断言，按领域分类标注
```

**执行方式**：串行。这是整个流程的入口，必须先完成。

**输出解析**：从 Critic 的输出中解析出每个断言的结构化数据（编号、原文摘录、类别、核查问题、建议核查路径）。

如果 Critic 返回的断言数量 < 5，重新执行一次 Critic，要求它更仔细地审查。

### 阶段 2：Verifier — 并行交叉验证

```
使用 Verifier System Prompt（prompts/verifier.md）
附录：所选领域的权威来源白名单、禁止引用列表、搜索偏好
对每个断言启动一个独立 SubAgent
SubAgent 需携带联网搜索能力
```

**执行方式**：所有 Verifier SubAgent 并行启动。

**关键要求**：
- 每个 SubAgent 使用**独立的对话上下文**（Agent 工具默认行为）
- 每个 SubAgent 携带 Verifier System Prompt + 领域配置 + 单个断言的数据
- SubAgent 需要联网搜索权限（WebSearch + WebFetch 工具）
- 禁止 Critic 的输出和原文全文进入 Verifier 上下文（仅携带其负责的单个断言）

**并发控制**：
- 默认同时启动全部 SubAgent
- 如果断言数量较多（>15），可分批启动（每批 10 个）

**输出收集**：等待所有 SubAgent 完成后，按编号收集核查结果。

### 阶段 3：Repairer — 自动修复

```
使用 Repairer System Prompt（prompts/repairer.md）
附录：所选领域的修复策略
输入：原始内容全文 + 所有核查结果
输出：修复报告 + 修复后内容
```

**执行方式**：串行。必须在所有 Verifier 完成后执行。

**筛选输入**：只将有问题的核查结果（⚠️ 不完整 / ❌ 错误 / ❓ 无法确定）传给 Repairer。✅ 准确的断言不需要修复。

### 阶段 4：报告

向用户展示：

1. **核查摘要**：
   - 领域：<所选领域>
   - 总共验证了 N 个断言
   - ✅ 准确：X 个
   - ⚠️ 不完整：Y 个
   - ❌ 错误：Z 个
   - ❓ 无法确定：W 个

2. **修复清单**：哪些问题已自动修复

3. **待人工确认项**：❓ 无法确定的内容

4. **输出文件**：
   - `article-verified.md`：修复后的内容
   - `verification-report.md`：完整核查报告（含所有断言 + 核查结论 + 来源）

## 用户交互规则

- **默认全自动执行**：Critic → Verifier × N → Repairer → 报告，中间不询问用户
- **如果用户说"先审再改"**：阶段 2 完成后暂停，展示核查结果让用户审核，由用户决定哪些要修复，再进入阶段 3
- **如果用户说"只查不改"**：跳过阶段 3，只输出核查报告
- **如果用户标注了特定关注点**（如"重点检查命令参数"、"重点核数据"）：在阶段 1 中将用户指示传递给 Critic
- **如果用户要求更换领域**：从阶段 0 重新开始

## 核心设计原则

1. **角色分离**：Critic 只提问不回答，Verifier 只核查不修改，Repairer 只修复不质疑
2. **上下文隔离**：每个 Verifier 独立上下文，避免 Critic 的偏见"传染"给 Verifier
3. **联网优先**：所有核查必须基于联网搜索结果，不得仅凭模型内置知识
4. **权威来源**：严格区分可信来源和内容农场，宁缺毋滥；以所选领域的白名单为准
5. **最小修复**：只改有问题的部分，保持原文风格
6. **领域配置优先**：`domains/` 中的领域配置覆盖通用 prompt 中与之冲突的规则

## 文件结构

```
verify-chain/
├── SKILL.md              # 入口 + 流程编排
├── README.md             # 使用说明
├── prompts/
│   ├── critic.md         # 通用 Critic 系统提示词
│   ├── verifier.md       # 通用 Verifier 系统提示词
│   └── repairer.md       # 通用 Repairer 系统提示词
└── domains/
    ├── _template.md      # 新领域配置模板
    ├── tech-article.md   # IT 技术文章（默认）
    ├── api-doc.md        # API / 库文档
    ├── product-spec.md   # 产品 PRD / 规格
    ├── sci-pop.md        # 科普 / 知识性内容
    ├── health-medical.md # 健康 / 医疗
    ├── finance-econ.md   # 财经 / 经济数据
    ├── exam-qna.md       # 面试 / 考试题库
    ├── tool-doc.md       # 工具使用文档
    ├── code-example.md   # 代码示例 / 教程中的代码
    ├── translation.md    # 翻译稿
    └── compliance.md     # 合规 / 安全 / 法规
```
